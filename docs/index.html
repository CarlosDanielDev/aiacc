why aiacc

Accounts, not acrobatics

Env-var juggling, symlinked credentials, a shell alias you half-remember — none of it. A profile is a directory; a command is a name.

one command per account

Type claude-work and Claude Code opens signed in as work. Tomorrow it still is. No switching, no re-login, no juggling.

one-step setup

aiacc setup installs a launcher per profile onto your PATH. They work immediately, in the shell you're already in — no sourcing, no reload.

interactive picker

A bare aiacc lists every profile with its login. Arrow keys to launch, a to add, r to rename, d to remove — all in the frame.

same skills everywhere

Profiles share your skills, sub-agents, slash commands and hooks, so claude-work is the same tool as claude — not an empty one.

your endpoint per profile

A profile can carry its own settings file: GLM, a proxy, any Anthropic-compatible API. --settings glm even generates the skeleton for you.

never touches credentials

aiacc points one environment variable at a directory and steps aside. Logins stay in each profile's own directory; aiacc never reads them.

quick start

Two accounts in a minute

No config file to write, no daemon, no shell plugin. Register, install the commands, type a name.

Register your accounts

Each gets its own isolated config directory — or run aiacc and press a.

aiacc add claude claude-work     --dir ~/.claude-work
aiacc add claude claude-personal --dir ~/.claude-personal

Install the launcher commands

One step. The commands work immediately — and add, remove and rename keep them in sync afterwards.

aiacc setup

Launch by name

The first run opens Claude Code signed out; /login once and that directory remembers it forever.

claude-work        # → /login as work, once
claude-personal    # a different account entirely

new

Hit a usage limit? Bring your own endpoint.

Some profiles differ in what they talk to, not who is logged in. Point one at GLM, a proxy or a gateway — the launcher passes its own settings file, layered over everything you share.

One keyword, one skeleton

glm writes the settings file for z.ai's Anthropic-compatible API — right base URL, right model, mode 600. custom leaves the base URL blank for you.

aiacc add claude claude-glm \
  --dir ~/.claude-glm --settings glm

Paste your key. That's it.

Open the generated file, replace the placeholder with your key. aiacc stores the path and never reads the file — your key never enters aiacc.

claude-glm         # Claude Code on GLM, from any directory

In the picker it's the same flow: press a and type glm in the settings field. An existing file is never overwritten — the add aborts and names the path.

how it works

One mechanism, honestly boring

Each account is an isolated config directory, selected by an environment variable. Claude Code reads CLAUDE_CONFIG_DIR; point it at ~/.claude-work and Claude runs as your work account. A launcher is a tiny script that sets that one variable for that one launch — → no global state, nothing to get out of sync, and your credentials are never touched. Codex and any other env-var-configurable CLI work the same way, out of the box.
